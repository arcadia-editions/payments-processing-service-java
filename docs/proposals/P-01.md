# P-01 asyncapi-client.yml has no channel for FulfillmentFailed and OrderConfirmationRejected

status: decided (A)
found by: pin to service-all 0.2.0, claude opus, 2026-11-25
flow: place-order-flow
blocks: T-27, T-28, T-29, T-30

## Problem
The ZFL voids the payment on three events
([place-order-flow.zfl:246](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L246)):
`when FulfillmentFailed, PaymentCaptureFailed, OrderConfirmationRejected do voidPayment`. The ZDL says so with three
`@asyncapi` on voidPayment
([payments-processing-api/domain-model.zdl:190](../../../payments-processing-api/domain-model.zdl#L190),
[:191](../../../payments-processing-api/domain-model.zdl#L191), [:194](../../../payments-processing-api/domain-model.zdl#L194)).
The released client contract (service-all 0.2.0,
[payments-processing-api/asyncapi-client.yml:14](../../../payments-processing-api/asyncapi-client.yml#L14)) has only
`fulfillment-scheduled-event-v1` and `order-created-event-v1`: no `order-confirmation-rejected-event-v1`
(orders-checkout-api asyncapi.yml:50) and no `fulfillment-failed-event-v1` (fulfillment-shipping-api asyncapi.yml:32).
The own-channel `payment-capture-failed-event-v1` is in `asyncapi.yml`, so only the two external ones are lost.
Root cause (confirmed): the client generator reads `$.options.asyncapi` of each method
(zenwave-sdk `ZDLToAsyncAPIClientGenerator.java` ~L100–134), and repeated `@asyncapi` keep only the LAST one; here the
last is the own channel, so no external channel of voidPayment reaches the client contract.

## Evidence
`mvn -DskipTests clean compile` generates `asyncapi.client.IFulfillmentScheduledEventV1ConsumerService` and
`IOrderCreatedEventV1ConsumerService` only; there is no `IFulfillmentFailedEventV1ConsumerService` nor
`IOrderConfirmationRejectedEventV1ConsumerService`, so this service never receives either event and a failed
fulfillment or a rejected confirmation never voids the authorization.

Repro: `jbang zw -p ZDLToAsyncAPIClientPlugin zdlFile=../payments-processing-api/domain-model.zdl targetFolder=<tmp>`
gives only fulfillment-scheduled and order-created. On a copy with the own-channel `@asyncapi` moved first,
fulfillment-failed (now last) appears and order-confirmation-rejected is still missing. catalog-inventory has the
same defect on `releaseStock` (its own P-01).

## Options
- A: fix the client contract generation (zenwave-sdk `ZDLToAsyncAPIClientPlugin`, one receive operation per external
  `@asyncapi`), regenerate payments-processing-api `asyncapi-client.yml`, release service-all 0.2.1, bump here and
  regenerate; then add stub adapters for the two new consumer interfaces. ZDL unchanged; fixtures unchanged.
- B: hand-add the two channels and receive operations to payments-processing-api `asyncapi-client.yml` and release
  0.2.1. Changes: contract only; drifts from the ZDL-generated file until A lands.

Recommendation: A, the ZDL already says the right thing; the contract should be generated from it.

## Decision
A, decided by the person 2026-11-26 (recorded by the orchestrator). The fix of zenwave-sdk ZDLToAsyncAPIClientPlugin
(one receive operation per external `@asyncapi`), the release of service-all 0.2.1 and the regeneration here are a task
of the next AFK loop. T-27..T-30 stay blocked in this loop.
