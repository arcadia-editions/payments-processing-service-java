# Arcadia Editions - Payments Processing Service (Java)

The payments processing bounded context as a standalone Java + Spring Boot microservice: clean hexagonal layout, PostgreSQL, Kafka with Avro events (Spring Cloud Stream). It is event-driven only: the OpenAPI has no REST operations (`paths: {}`). Created from the ZenWave java archetype; the code is generated from the domain model and the API contracts in [payments-processing-api](https://github.com/arcadia-editions/payments-processing-api) with the ZenWave SDK.

> [!IMPORTANT]
> **This repository contains only code generated by the [ZenWave SDK](https://www.zenwave360.io/).** The business behavior was **not** implemented: service methods are still the generated `TODO`s.
> For a fully implemented version (the same bounded contexts, with `place-order-flow` implemented using [zenwave-sdd](https://github.com/ZenWave360/zenwave-sdd)), see the modulith: **[arcadia-editions-modulith-service-java](https://github.com/arcadia-editions/arcadia-editions-modulith-service-java)**.

## Getting Started

```bash
docker-compose up -d     # local infrastructure (PostgreSQL, Kafka, Schema Registry)
mvn spring-boot:run
```

* Actuator: http://localhost:8080/actuator

## Prerequisites

* Java 25+
* Maven 3.6+
* Docker / Docker Compose (local infrastructure and integration tests)
* Git and Git Bash (all commands below are Git Bash)
* JBang and the ZenWave CLI (`jbang zw`), see [Install the ZenWave tooling](#install-the-zenwave-tooling)
* IntelliJ IDEA (or VS Code) with the ZenWave plugin, for editing `.zdl` / `.zw` files and running the generators
* SDKMAN! (optional, recommended for Java and Maven)

## Project Structure

Files at the project root:

| Path | Purpose |
|---|---|
| models (not in this repo) | `domain-model.zdl`, `openapi.yml`, `asyncapi.yml`, `asyncapi-client.yml` and Avro schemas in [payments-processing-api](https://github.com/arcadia-editions/payments-processing-api), read from their raw GitHub URLs (branch `main`) |
| `zenwave-scripts.zw` | the ZenWave SDK plugins to run against the model, with their configuration |
| `pom.xml` | build, dependencies and the OpenAPI / AsyncAPI generators; base packages and contract URLs in `<properties>` |
| `docker-compose.yml` | local infrastructure (PostgreSQL, Kafka, Zookeeper, Schema Registry) |
| `src/main/java/<package>/config` | Spring configuration (security, async, database, web, exception translation...) |
| `src/main/resources/application*.yml` | application configuration (`application-default.yml` for local runs) |
| `src/test/resources/application-test.yml` | test configuration |
| `target/generated-sources/{openapi,zenwave}` | code generated on every build, never edited by hand |

The rest of the code is generated from the model with `CleanHexagonalProjectLayout` (base package `com.arcadiaeditions.payments.processing`):

| Package | Contents |
|---|---|
| `core` | domain model (`Payment` + state transitions), inbound port `PaymentsProcessingService` and its DTOs, outbound Spring Data repository (`core.outbound.jpa`), application service and mappers (`core.application`) |
| `adapters` | inbound adapters; empty for now (no web controllers: the OpenAPI has no operations) |
| `infrastructure` | outbound adapter implementations; empty for now (only `package-info.java`) |
| `asyncapi.provider` | generated AsyncAPI SDK for `asyncapi.yml` (events this service publishes), outside the hexagon |
| `asyncapi.client` | generated AsyncAPI SDK for `asyncapi-client.yml` (events this service consumes, e.g. `FulfillmentScheduled`), outside the hexagon |

Keep the `layout.*` values in `zenwave-scripts.zw` matching the `openApi*` / `asyncApi*` package properties in `pom.xml`.

## Code Generation

Code comes from two places: the ZenWave SDK, run from `zenwave-scripts.zw` when the domain model changes, and Maven plugins that run on every build for the API contracts.

### From the domain model: zenwave-scripts.zw

The OpenAPI / AsyncAPI contracts are produced in [payments-processing-api](https://github.com/arcadia-editions/payments-processing-api), not here. The plugins in `zenwave-scripts.zw`, in the order to run them:

| Plugin | Generates |
|---|---|
| `BackendApplicationDefaultPlugin` | domain entities, repositories, services and their implementations, DTOs, mappers, events, listeners, in-memory test configs and tests |
| `OpenAPIControllersPlugin` | Spring MVC controllers implementing the OpenAPI interfaces (nothing while the OpenAPI has no operations) |
| `SpringWebTestClientPlugin` | API tests (per operation, and per business flow) |

**How to run them:** open `zenwave-scripts.zw` in the IDE with the ZenWave plugin and use the play button next to each plugin. Hovering the button shows the equivalent command line (`jbang zw -p <Plugin> --deps <...> key=value ...`), which you can copy and run from a terminal. `jbang zw` doesn't take a `.zw` file directly: each plugin block is one command.

After generating:

```bash
mvn -DskipTests clean test-compile    # also runs the Maven generators below
git add -A && git commit -m "feat: generate code from the payments-processing models"
```

**Regenerating safely.** Some files are *generated once* and then belong to you: service implementations, event listeners and their MapStruct mappers, tests, `src/test/resources/data*` and `DockerComposeInitializer`. A normal run doesn't touch them. A run with `--force` / `-f` overwrites them, so check the command the IDE generates, and run `git diff` after every regeneration.

### At build time: OpenAPI and AsyncAPI (Maven)

These run in `generate-sources` on every `mvn compile`, from the contract URLs in `pom.xml`. Their output goes to `target/` and is never edited by hand.

**OpenAPI** (`openapi-generator-maven-plugin`, generator `spring`):
* reads `openapi.yml` from payments-processing-api (`openapi.inputSpec`);
* generates the Spring MVC API interfaces and the `*DTO` models into `target/generated-sources/openapi` (`interfaceOnly`: the controllers from `OpenAPIControllersPlugin` implement them);
* packages are set by the `openApiApiPackage` / `openApiModelPackage` properties in `pom.xml`.

**AsyncAPI** (`zenwave-sdk-maven-plugin`, generator `AsyncAPIGenerator`), two executions, both with role `provider`:
* `generate-asyncapi`: `asyncapi.yml` (events this service publishes) into `asyncapi.provider`;
* `generate-asyncapi-client`: `asyncapi-client.yml` (events this service consumes, written from its point of view) into `asyncapi.client`;
* payloads are Avro; if a schema references another by name, list the referenced `.avsc` URLs (dependencies first) in `avroCompilerProperties.imports`;
* output goes to `target/generated-sources/zenwave`. See the [AsyncAPI generator docs](https://www.zenwave360.io/zenwave-sdk/plugins/asyncapi-generator/).

## Testing

* JUnit 5 and Spring Boot Test
* In-memory implementations of repositories for fast unit tests (generated by ZenWave SDK)
* Testcontainers with docker-compose for integration tests (e.g. `PaymentRepositoryIntegrationTest`)
* ArchUnit for architecture rules (`ArchitectureTest`)
* JaCoCo coverage report on `mvn verify`

Naming: `*Test` runs with Surefire (`mvn test`); `*IT` and `*IntegrationTest` run with Failsafe (`mvn verify`).

Rules of thumb:

* Favor functional, vertical (acceptance) tests over unit tests where every dependency is mocked.
  * Use `@SpringBootTest` for the most important use cases.
  * Use the in-memory dependencies for all use cases.
* Adapters that connect to external resources **must** be tested against real infrastructure (Testcontainers), even if it doesn't add coverage.
* Mockito is a last resort; prefer in-memory repositories and WireMock.

[Spotless](https://github.com/diffplug/spotless) with Palantir Java Format:

```bash
mvn spotless:apply     # format

```

IDE plugins: [palantir-java-format for IntelliJ](https://plugins.jetbrains.com/plugin/13180-palantir-java-format) (enable it per project in `Settings → palantir-java-format Settings`) or the [Eclipse plugin](https://github.com/palantir/palantir-java-format/tree/develop/eclipse_plugin). Keep a consistent code style from the beginning of the project.

## Spec-Driven Development with zenwave-sdd

The generator creates the structure: entities, services, events, mappers and test skeletons, and leaves the behavior as `TODO`s (as they are in this repository). To complete it with AI coding agents (Claude Code, Codex, Grok...) and GitHub Spec Kit, follow **[zenwave-sdd](https://github.com/ZenWave360/zenwave-sdd)**: installing the skills, configuring the project overlay, and the full workflow in the [zenwave-sdd manual](https://github.com/ZenWave360/zenwave-sdd/blob/main/MANUAL.md). For a worked example, see [arcadia-editions-modulith-service-java](https://github.com/arcadia-editions/arcadia-editions-modulith-service-java).

The rule: **models own structure.** If a behavior needs a field, event, command or state that the ZDL doesn't have, fix the ZDL in [payments-processing-api](https://github.com/arcadia-editions/payments-processing-api) and regenerate. Never hand-add it to code.
